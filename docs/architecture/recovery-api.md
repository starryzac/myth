# 模拟安全恢复接口

MVP-205 已验证的接口合同。全部数据来自合成模拟用户和本地 PostgreSQL；无真实银行连接。完整验收记录见 `docs/progress/MVP-205.md`。

| 方法与路径 | 作用 | 数据写入 |
| --- | --- | --- |
| `GET /api/v1/recovery/preview` | 从服务器事实、时间和原始/当前授权生成恢复预览 | 无 |
| `POST /api/v1/recovery/runs` | 建立恢复记录，执行获准的整仓无损动作；重放原键可对账已受理请求 | 明确的应用、银行、应用投影三段事务 |
| `GET /api/v1/recovery/runs/{run_id}` | 查询该用户原始计划、当前实际边界、银行状态、回执和本地通知 | 无；即使T1已经到期也不推进结算 |

POST 唯一可接受的请求字段是 `idempotency_key`，要求非空白字符串，长度1–160字符，保存原值并派生固定长度的内部键。服务端决定用户、仓位、本金、条款、权限、时钟和到账时点。三个接口均拒绝额外查询参数，POST拒绝额外JSON字段；不提供用 `accepted=true` 绕过有损确认的入口。

```json
{"idempotency_key":"recovery-demo-001"}
```

预览返回 `plan.actual_boundary` 与 `plan.projected_boundary`。执行记录中的 `plan` 保留首次决策事实；顶层 `actual_boundary` 是查询时重新计算的实际边界。预计安全、银行受理、银行到账和应用对账是不同事实，不能相互替代。

T0在银行两条本金减少/现金增加分录提交并完成应用对账后产生唯一回执及 `PRINCIPAL_RECEIVED` 本地通知。T1受理时为 `PENDING_SETTLEMENT`，本金仍被占用，应用现金不增加；可查询 `REDEMPTION_ACCEPTED` 通知。再次POST原键才会查询原请求并在到期后消费银行分录。不能换键代替未知请求的对账。

只有最新实际边界为READY且所有动作已到账对账时，结果才可为RECOVERED。固定种子覆盖不会随服务器时间自动延长；到账后若历史完整性或其他来源仍不足，不能只凭成功回执声称风险消失。

未知记录和其他用户记录均返回统一NOT_FOUND；读接口不通过错误响应泄露别人的恢复内容。无风险请求也有可查询记录，但不生成银行动作。基线种子的三笔人工旧版本持仓没有原购买自动恢复授权，不能用新建通用策略追认自动赎回。

对应真实PostgreSQL接口验证在 `apps/api/app/tests/test_recovery_api.py`；金额/时间覆盖、跨用户隔离、最大键长、无风险重放、应用余额篡改、T0整仓返本与T1只读查询均已建立测试。完整失败注入、并发、自然到期及权限矩阵由服务/域测试共同验收，不能仅用这些HTTP用例宣称MVP-205完成。
