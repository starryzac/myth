# 《钱途有界》完整开发计划（Codex 执行版）

> **副标题：面向青年的可审计分级自主资金 Agent**  
> **内部代号：BoundedFunds Full**  
> **版本：v1.0 / 带拓展的完整研究与竞赛交付计划**

---

## 0. 本计划与初版计划的关系

本计划以《钱途有界_初版开发计划_Codex执行版.md》为前置基础，不推翻初版边界，而是在其上完成以下升级：

- 从单用户、少量策略扩展到多账户、多目标、多策略冲突；
- 从简单规则编译扩展到“自然语言候选策略编译 + 严格结构化确认”；
- 从单产品选择扩展到受约束的多资产配置与定存梯度；
- 从简单边界重算扩展到事件驱动、可回放的完整资金状态机；
- 从规则式询问扩展到“只问能区分决策的最小问题”；
- 从普通日志扩展到双时态事实、策略版本、动作回执和可验证审计链；
- 从演示案例扩展到冻结场景集、性质测试、消融实验和青年用户研究；
- 从竞赛企划书扩展到竞赛版、技术白皮书、证据包和答辩材料的完整交付。

完整版本仍坚持以下不可变边界：

1. **不做跨行聚合。** 现在和未来都围绕工行体系内可确认事实、可执行动作和产品闭环。
2. **不以未来未到账收入扩大当前自主资金。** 这不是 MVP 临时保守，而是长期风险原则。
3. **不做生活服务。** 不点外卖、不推荐商户、不替用户评价普通消费。
4. **不让 Agent 自主产生新的对外付款意图。** 新收款关系和临时转账必须由用户发起。
5. **不让 LLM 决定金融后果。** LLM 只能生成候选结构和解释，确定性引擎掌握金额、约束、权限、状态和执行。
6. **不允许高风险资产进入自主执行路径。** 本金波动型产品只能作为人工决策辅助的未来接口，不能自动购买。
7. **目标归属和资产放置严格分离。** 已归属目标的资金默认不可跨目标挪用。
8. **任何自主动作必须可追溯。** 无证据、无策略版本、无回执的动作一律不可执行。

## 1. 项目最终定义

### 1.1 名称

# **钱途有界**

### 1.2 一句话定义

> 以工行可信账户事实为底座，将青年用户的自然语言生活目标编译成可理解、可版本化的动态资金策略；系统在固定资金义务、基本生活准备金、目标储备、资产流动性和用户授权共同构成的边界内，自主完成严肃资金动作与低风险资金配置，并仅在新事实真正改变可执行动作集合时请求最小必要人工介入。

### 1.3 产品核心不是“理财推荐”

完整版本研究的对象是：

> **一个银行 Agent 如何在不越权、不侵占受保护资金、不依赖未到账收入的前提下，获得尽可能大的持续自主性。**

系统优化的不是“收益最大化”，而是一个有顺序的目标：

1. 不违反硬约束；
2. 不越过用户授权；
3. 保障流动性和可恢复性；
4. 减少不必要人工介入；
5. 在全部约束满足后，提高低风险资金使用效率；
6. 保留完整、可核验的决策证据。

### 1.4 主赛道与扩展方向

- 主赛道：青年群体服务；
- 技术副标签：金融安全、数字金融；
- 扩展场景：个体经营者、小微商户经营现金流；
- 扩展原则：替换义务和目标类型，不重写底层自主边界引擎；
- 不采用“青年＋普惠双主赛道”叙事，避免产品焦点分散。

## 3. 完整产品范围

### 3.1 工行事实底座

完整版本支持模拟的工行内部对象：

- 活期/工资账户；
- 本行信用卡账单与自动还款；
- 本行目标储备子账户；
- 本行现金管理账户；
- 本行定期存款；
- 有限期限、低风险、属性明确的模拟产品；
- 固定收款关系；
- 用户主动发起的临时转账；
- 产品申购、赎回、到期和提前支取模拟回执。

### 3.2 用户未来意图

银行看不到但用户可主动补充：

- 黄金周、春节返乡等有日期计划支出；
- 演唱会、考试、搬家、旅行等事件资金；
- 买房、买车、换电脑等长期目标；
- 外部义务，但只作为用户声明，不假装银行已经核实；
- 对策略的持续时间、优先级、可削减性、可延期性和授权范围。

### 3.3 策略模板

完整版本最多支持以下有限模板，不支持任意自然语言程序：

1. `RecurringObligationPolicy`：房租、账单、还款；
2. `LivingReservePolicy`：动态生活准备金；
3. `EmergencyBufferPolicy`：应急缓冲；
4. `DatedExpensePolicy`：国庆、春节、演唱会等有日期支出；
5. `LongTermGoalPolicy`：买车、买房等长期目标；
6. `PeriodicTransferPolicy`：已确认固定收款关系；
7. `AssetAuthorizationPolicy`：允许资产、额度、锁定和赎回边界；
8. `RecoveryPolicy`：何时允许自动赎回；
9. `GoalAllocationPolicy`：新增资金如何在多个目标间分配；
10. `CrossGoalReallocationPolicy`：默认关闭，用户显式开启后才允许特殊回拨；
11. `SeasonalReservePolicy`：节假日历史支出调整建议；
12. `InterventionPolicy`：哪些变化必须重新询问。

### 3.4 自主动作

完整版本只允许 Agent 自主产生：

- 预授权周期义务支付；
- 预授权固定收款关系转账；
- 目标储备划转；
- 本人账户之间调拨；
- 低风险产品申购；
- 预授权、无显著损失的安全恢复赎回；
- 到期资金再配置；
- 在用户确认范围内调整目标月度储备节奏。

临时对外转账必须由用户主动发起；新的收款人、越权金额、关键字段歧义或新的损失后果均需人工确认。

## 5. 证据、事实与时间模型

### 5.1 双时态事实

每条重要事实至少记录：

- `valid_from / valid_to`：事实在现实中何时有效；
- `observed_at`：系统何时知道它；
- `source_type`；
- `source_ref`；
- `content_hash`；
- `evidence_level`；
- `supersedes_id`。

这样系统能够回答：

> “在当时已知的信息下，为什么这个动作是合理的？”

而不是拿今天才知道的信息反向解释过去。

### 5.2 证据规则

- `BANK_CONFIRMED` 可直接用于硬事实；
- `BANK_OBSERVED` 只能生成候选策略；
- `USER_DECLARED` 可进入方案模拟，但未确认前不能形成持续权限；
- `MODEL_INFERRED` 只能提出建议或问题；
- `USER_CONFIRMED_POLICY` 才能持续约束或授权 Agent；
- 冲突证据不得静默覆盖，必须产生 `CONFLICTED` 状态；
- 证据不足时保留 `UNKNOWN`，不得用模型补全。

### 5.3 策略版本

每次修改生成不可变 `PolicyVersion`：

- 版本号；
- 结构化配置；
- 自然语言摘要；
- 用户确认记录；
- 生效和失效时间；
- 修改原因；
- 依赖证据；
- 前一版本哈希；
- 影响分析。

策略版本改变后：

1. 未提交动作失效；
2. 在途动作重新核对权限；
3. 边界重算；
4. 已有持仓检查是否仍满足策略；
5. 必要时触发安全恢复或人工确认。

## 6. 自然语言策略编译

### 6.1 原则

用户表达可以丰富，内部策略语言必须有限、透明、可校验。

示例：

> “国庆去重庆玩，最好给我留三千到四千，别影响房租。”

候选编译为：

```json
{
  "template": "dated_expense",
  "name": "国庆重庆旅行",
  "window": {"start": "2027-10-01", "end": "2027-10-07"},
  "amount": {"min_cents": 300000, "target_cents": 350000, "max_cents": 400000},
  "priority": {
    "importance": 45,
    "minimum_cents": 300000,
    "reducible": true,
    "deferrable": false
  },
  "must_not_reduce_policy_ids": ["rent_policy"],
  "evidence_level": "MODEL_INFERRED",
  "requires_confirmation": true
}
```

### 6.2 编译流水线

```text
自然语言
→ PII脱敏
→ 候选实体和时间提取
→ 策略模板选择
→ 严格 JSON Schema 校验
→ 冲突/缺失检测
→ 人类可读摘要
→ 用户修改与确认
→ USER_CONFIRMED_POLICY
```

### 6.3 编译器实现

定义接口：

```python
class PolicyCompiler(Protocol):
    def compile(self, text: str, context: CompileContext) -> PolicyProposal: ...
```

实现：

- `RuleBasedPolicyCompiler`：稳定基线；
- `LLMPolicyCompiler`：可选，输出严格结构；
- `PolicyProposalValidator`：独立校验；
- `PolicyDiffExplainer`：展示用户确认前后的差异。

LLM 生成结果必须：

- 通过 JSON Schema；
- 不得直接进入 `ACTIVE`；
- 对金额和日期缺失输出问题，不得猜；
- 附带来源文本片段；
- 与规则编译器冲突时进入人工确认。

## 7. 策略发现

### 7.1 周期规律发现

从银行历史数据发现候选：

- 固定日期附近相似金额；
- 相同收款人或账单机构；
- 连续多周期出现；
- 金额方差在阈值内；
- 交易类型稳定。

输出只能是：

> “我发现一个可能需要持续预留的规律，是否建立策略？”

不得直接建立未来义务。

### 7.2 节假日和事件建议

系统可结合：

- 公共日历中的春节、国庆等已知窗口；
- 用户过去相似时段的本行消费；
- 用户主动声明的旅行或活动；

生成“临时准备金调整”候选。

不能仅因为节日将所有用户准备金自动提高；必须展示依据并首次确认。

### 7.3 目标发现边界

系统不得从一次购买记录推断用户的人生目标。长期目标只允许：

- 用户主动创建；
- 用户明确表达后由编译器生成候选；
- 用户确认后生效。

## 8. 现金流与自主边界引擎

### 8.1 时间离散

- 默认按日建模；
- 近期 30 天可按小时扩展，但完整版本不强制；
- 默认投影 365 天；
- 自动执行边界使用未来收入为 0 的保守投影；
- 另可展示“规划视图”，但规划视图不得驱动自动动作。

### 8.2 资金类别

```text
LiquidCash                当前可立即支付现金
ProtectedObligation       已确认固定资金义务
LivingReserve             用户确认的动态生活准备金
EmergencyBuffer           应急缓冲
GoalOwnedFunds             已归属目标资金
AutonomousIdleFunds        可由 Agent 自主配置的资金
HumanControlledFunds       超出 Agent 授权的资金
```

### 8.3 边界定义

Agent 真正可操作区域：

```text
AutonomyEnvelope
= FinanciallySafeSet
∩ UserAuthorizedSet
∩ LiquidityCompatibleSet
∩ EvidenceSufficientSet
∩ SupportedActionSet
```

任何一个集合不满足，均不得自主执行。

### 8.4 现金流不变量

必须由性质测试验证：

1. 任何自动动作后，所有硬义务在其截止日前均有可用现金覆盖；
2. 未来收入变化不影响当前自主资金；
3. 目标已归属资金不会被低优先级动作占用；
4. 策略版本失效后不再产生新权限；
5. 产品在赎回可用前不计入现金；
6. 需要有损提前支取的资产不会自动充当安全现金；
7. 动作重试不会产生重复副作用。

## 9. 多目标约束与资金分配

### 9.1 目标属性

每个目标包含：

- 目标金额；
- 目标日期；
- 当前已归属资金；
- 月度最低/建议/最高储备；
- 用户确认的重要程度；
- 最低保障额；
- 是否允许部分满足；
- 是否允许延期；
- 延期成本；
- 资产策略；
- 是否允许跨目标回拨；
- 有效策略版本。

### 9.2 新增资金分配

只对“新增且尚未归属”的安全资金做分配。

使用词典序优化：

1. 硬义务零违反；
2. 应急与生活准备金零违反；
3. 各目标最低储备短缺最小；
4. 高优先目标的加权缺口最小；
5. 总目标延期最小；
6. 在授权范围内接近 `target`；
7. 不超过 `max`；
8. 资金调动次数最少。

### 9.3 已归属资金

默认规则：

- 目标内可改变资产放置；
- 不可自动改变目标归属；
- 只有用户预先确认 `CrossGoalReallocationPolicy` 时，才能在特定紧急条件下回拨；
- 未授权时系统只能提出建议。

### 9.4 冲突最小修复

当全部策略不可同时满足时：

1. 构建约束集合；
2. 找到不可满足的最小冲突集；
3. 只针对允许调整的策略生成修复候选；
4. 以“改动策略数量最少、总偏离最小、优先级损失最小”为目标排序；
5. 向用户展示：哪些策略不冲突，哪些策略必须调整；
6. 用户确认后生成新策略版本。

示例输出：

> 房租、信用卡和生活准备金仍可完整满足。冲突只涉及“买车本月储备2000”和“国庆旅行储备1500”。建议将本月买车储备调整为1800、旅行储备调整为900。其他策略不变。

## 10. 资产池与优化

### 10.1 完整资产类别

自主路径仅支持：

- `CASH`；
- `CASH_MGMT_T0`；
- `CASH_MGMT_T1`；
- `FIXED_DEPOSIT_7D`；
- `FIXED_DEPOSIT_30D`；
- `FIXED_DEPOSIT_90D`；
- `LOW_RISK_TERM`：属性明确、无本金波动的模拟有限期限产品。

本金波动产品：

- 可在未来 UI 中展示为 `ADVISE_ONLY`；
- 不进入自动资产优化；
- 不作为本项目完整版本的核心交付。

### 10.2 产品属性

每个产品必须有：

- 风险等级；
- 是否本金波动；
- 起投金额；
- 锁定期；
- 赎回时延；
- 到期规则；
- 提前支取规则；
- 提前支取损失；
- 模拟收益；
- 是否可自动申购；
- 是否可自动赎回；
- 产品版本和生效日期。

### 10.3 优化目标

在所有硬约束满足后，按以下顺序：

1. 不产生未授权损失；
2. 满足目标资金使用日期；
3. 保持安全恢复能力；
4. 最大化确定性净模拟收益；
5. 减少资产切换和费用；
6. 并列时优先流动性更高的产品。

### 10.4 定存梯度

对于长期目标，可生成定存梯度：

- 不同批次在目标日期前陆续到期；
- 每批不超过该目标资产策略；
- 不能把即将使用的资金锁入长期定存；
- 到期后是否再配置由当时策略重新决定；
- 提前支取损失默认要求人工确认。

## 11. 最小必要人工介入算法

这是完整版本相对普通预算工具和静态 Agent 的核心研究模块。

### 11.1 问题定义

不是“模型置信度低就问”，而是：

> **只有尚未确定的信息会改变 Agent 的动作类别、动作金额、资金归属或风险后果时，才值得询问。**

### 11.2 不确定变量

可能包括：

- 用户指令指向哪个固定收款关系；
- 某个计划支出的金额区间；
- 某个目标是否仍有效；
- 房租是否续租；
- 是否允许承担定存提前支取损失；
- 新策略的持续时间；
- 用户对策略调整的选择。

### 11.3 无概率的稳健问题选择

由于项目坚持风险优先，初始版本不依赖概率模型。

算法：

1. 为每个不确定变量建立有限候选值；
2. 对候选组合分别运行确定性决策引擎；
3. 记录每个世界中的动作结果；
4. 若所有世界产生相同动作，则不询问；
5. 若动作不同，寻找能最大程度区分动作集合的问题；
6. 采用 minimax：使“回答后剩余最大动作分歧”最小；
7. 一次只问一个问题；
8. 得到回答后重新计算，而不是沿用旧候选。

返回：

```json
{
  "should_ask": true,
  "question": "你说的月底固定支出是1800元房租还是1200元信用卡还款？",
  "reason": "不同回答会使当前可自主资金相差600元并改变资产配置动作",
  "affected_actions": ["asset_purchase", "goal_contribution"],
  "alternatives": [...]
}
```

### 11.4 边界跨越触发

只有以下情况触发用户介入：

- 当前自主金额需要下降；
- 已有资产需要赎回；
- 某个 `AUTO_EXECUTE` 动作变成不可执行；
- 某个目标最低约束无法满足；
- 需要新收款关系、新资产类别、新损失或新风险；
- 需要修改用户价值偏好；
- 策略发生冲突且无预授权修复规则。

仅数字变化但不改变动作集合时，静默更新并记录。

## 12. 动作执行与状态恢复

### 12.1 动作状态机

```text
DRAFT
→ PLANNED
→ AUTHORIZED
→ SUBMITTED
→ SUCCEEDED / TERMINAL_FAILED / UNKNOWN
→ RECONCILED
```

- `UNKNOWN` 不能当作失败，也不能盲目重试；
- 每个动作有业务 `root_id`、策略版本、尝试 `attempt_id` 和幂等键；
- 模拟账本必须是独立真值，不以应用日志判断成功。

### 12.2 支持动作

- `TRANSFER_INTERNAL`
- `PAY_RECURRING_OBLIGATION`
- `TRANSFER_TO_CONFIRMED_PAYEE`
- `ALLOCATE_TO_GOAL`
- `PURCHASE_ASSET`
- `REDEEM_ASSET`
- `OPEN_FIXED_DEPOSIT`
- `MATURE_FIXED_DEPOSIT`
- `EARLY_WITHDRAW_FIXED_DEPOSIT`

### 12.3 安全恢复

边界收缩时：

1. 计算缺口；
2. 优先使用未配置自主现金；
3. 再赎回 T+0；
4. 再赎回 T+1；
5. 再使用已到期定存；
6. 提前支取定存若有损失，转人工；
7. 恢复后生成完整回执；
8. 若来不及恢复，进入 `LIQUIDITY_RISK`，提供可选方案，不虚构已解决。

### 12.4 对账

动作完成后必须核对：

- 模拟账户余额；
- 目标归属；
- 资产持仓；
- 动作回执；
- 决策预期与实际效果；
- 是否发生重复副作用。

## 16. 安全、隐私与合规边界

### 16.1 数据最小化

- 原始交易说明和个人标识默认不发送给外部模型；
- 策略编译前脱敏；
- 模型只接收完成任务所需的最少字段；
- 导出证据包默认使用合成或脱敏数据；
- 日志不得记录完整账号、手机号或身份证号。

### 16.2 权限

角色：

- `USER`
- `REVIEWER`
- `SYSTEM`
- `DEMO_ADMIN`

任何资金动作必须绑定：

- 发起主体；
- 授权来源；
- 策略版本；
- 幂等键；
- 动作范围。

### 16.3 威胁模型

至少覆盖：

- 提示注入试图修改策略；
- LLM 输出越权字段；
- 旧策略重放；
- 审计记录篡改；
- 重复动作；
- 资产产品版本漂移；
- 用户撤销策略后的在途动作；
- 前端伪造解释；
- 数据库状态与动作回执不一致。

### 16.4 声明边界

完整版本仍不得宣称：

- 已符合真实银行生产安全要求；
- 已通过监管或法律审查；
- 已提供正式投资建议；
- 已接入真实工行系统；
- 已改善真实客户收益；
- 已覆盖所有青年生活情景。

正式落地前必须由银行业务、消保、合规、安全和产品人员分别审查。

## 21. 工行价值与落地路径

### 21.1 为什么是银行 Agent

- 银行拥有账户、账单和资产的可信事实；
- 银行能执行内部划转、产品配置和回执；
- 用户未来目标弥补银行不可观测信息；
- 决策可从事实一直追到金融动作；
- 不需要通过跨行和生活服务争夺入口。

### 21.2 业务假设

以下均是待验证假设，不写成既成事实：

- 青年用户愿意用少量策略确认换取持续资金管理；
- 可审计自主动作可能增强控制感和信任；
- 合适的低风险产品可在更透明的条件下触达；
- 减少无意义确认可能提高持续使用率；
- 动态目标储备可能提高青年用户资金规划黏性。

### 21.3 试点顺序

1. 完全模拟；
2. 工行员工/学生志愿者的合成账户测试；
3. 只读账户事实、无真实交易的影子模式；
4. 小额内部划转沙箱；
5. 经业务、消保、安全和合规审查后再讨论真实动作。

## 23. 关键风险与停止条件

### 23.1 技术风险

- 多目标优化无法解释；
- 问题选择只是在包装置信度；
- 定存和流动性模型不一致；
- 动作状态与账本不一致；
- 策略版本不能稳定回放；
- 审计只是日志，没有事实和理由。

### 23.2 产品风险

- 用户配置负担接近传统预算 App；
- Agent不断弹窗，失去自主性；
- 自动动作过多，用户失去控制感；
- 项目变成理财产品推荐；
- 项目扩成生活服务或跨行聚合；
- 青年场景只是标签，实际问题仍不具体。

### 23.3 停止或降级条件

- 若静态规则在相同安全水平下已达到相同介入次数，则降低“智能策略”主张；
- 若最小问题算法不能优于全量确认，则保留审计和边界引擎，删除过度研究包装；
- 若用户无法理解动态策略授权，改用更少模板；
- 若多资产优化无法稳定解释，退回单产品选择；
- 若定存恢复边界无法正确处理，初版只保留到期管理，不展示自动提前支取；
- 若任何冻结案例出现硬约束违反，停止写效果结论。
