## 执行与返回值

数据库须先完成迁移。在仓库根使用统一入口 `make seed` / `.\make.cmd seed`，或已迁移后直接执行：

```powershell
uv run --cache-dir .uv-cache --frozen python scripts/seed_demo.py
```

服务接口是 `seed_demo(engine: Engine) -> SeedSummary`，不会执行 DDL、回滚迁移或删除数据库。配置由现有 `.env` 读取；输出为可序列化的 Pydantic 模型，CLI 打印 JSON。固定日期导出为 ISO 字符串，金额均为整数分。

| 字段 | 意义 |
|---|---|
| `simulation` | 恒为 true。 |
| `seed_version`、`user_id`、`as_of` | 种子版本、演示身份、观察截止。 |
| `period_start`、`period_end`、`days` | 连续本地日期范围及 60 天长度。 |
| `counts` | 16 张核心表内本演示数据的行数；产品只统计这套种子的 3 个固定 ID，不包括其他全局产品。 |
| `cash_balance_cents` | 五账户已记账现金之和。 |
| `asset_principal_cents`、`asset_yield_cents` | 未赎回合成持仓本金与已累计模拟收益。 |
| `total_asset_cents` | 现金加持仓本金及累计收益；没有再次加目标归属金额。 |
| `credit_card_unpaid_cents` | 账单总额减已还金额，独立展示负债。 |
| `dataset_sha256` | 演示行及固定产品行按表/ID排序后，以稳定 JSON 编码计算的 SHA-256；不包括其他用户的数据。 |

## 种子内容

实测生成 1 个用户、5 个账户、129 条交易、252 条证据、3 张信用卡账单、3 个投资产品、3 笔持仓。策略、版本、目标对象、候选、决策、动作和审计事件均为 0。目标账户中的钱来自用户历史手动划转，不表示已经授予 Agent 持续权限。

五账户为活期、目标储备、信用卡、现金管理、定存。现金管理与定存账户的现金余额初始为零；产品本金单独记在持仓中。信用卡负债由账单表达，不伪造负的现金余额。

## 投资产品与事实边界

现金基准是活期账户，不额外占用“恰好三个投资产品”的数量。

| 合成产品代码 | MVP 资产类别 | 本金（分） | 模拟年化基点 | 赎回/锁定 |
|---|---|---:|---:|---|
| `BF_DEMO_T0` | `CASH_MGMT_T0` | 250,000 | 150 | T+0，无锁定 |
| `BF_DEMO_T1` | `CASH_MGMT_T1` | 150,000 | 180 | T+1，无锁定 |
| `BF_DEMO_FIXED_30D` | `FIXED_DEPOSIT` | 100,000 | 220 | 锁定 30 天，9 月 25 日购入；提前支取损失设为本金的 20 基点 |

这些数值是固定测试条件，不代表银行在售产品或收益承诺。最低起投均为 10,000 分，风险级别 0、本金波动 false；产品能力标志不等于用户授权。定存提前赎回不允许自动执行。

初始累计收益设为 0，不把展示年化乘出来的未来收益当成现金。三笔持仓均为 HELD，尚未赎回，`available_at` 为 null，包括 T+0。定存到期日是合约条件，当前仍不得计入可支付现金。

所有银行事实均显式标记合成来源。仅 food、transport、daily_necessities 的 `category_confirmed` 为 true，并各自另存 `USER_DECLARED` / `SIMULATED_USER_CATEGORY_CONFIRMATION` 证据，记录合成用户、分类、关联交易和确认依据。银行余额/交易证据为独立的 BANK_CONFIRMED；用户类别确认不是策略确认，不产生 ACTIVE 权限。所有已发生交易、观察时间与确认时间不晚于固定观察截止，不导入未来工资。

## 重置保护

重置在一个 PostgreSQL 事务内获得专属 advisory transaction lock，串行化同种子的并发重置。先核验固定 ID 与外部标识同时属于合成身份；任何不匹配或非模拟身份均拒绝，不覆盖占用者。

只清理固定演示用户的数据，按审计→回执→动作→约束→持仓→目标→交易/账单→候选/版本/策略→决策→证据→账户→用户的引用顺序执行。审计原因链和证据 supersedes 自引用在同一事务中先解除，再删除所属演示行。未来只追加审计机制上线后需要专门的、可审计的演示重置流程；当前机制不能冒充审计只追加控制。

全局产品不删除、不覆盖。固定产品如已存在，要求所有固定属性一致才能复用；内容漂移或 ID/产品代码冲突会使整次操作失败，保留原数据和其他用户引用。其他用户、其他产品均保持不变。任意中途异常回滚整次删除与插入，错误向调用方传播。
