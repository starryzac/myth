> **副标题：面向青年的可审计分级自主资金 Agent**

## 0. 项目重新命名与一句话定义

原名称“声令消歧”已经不足以覆盖重新定义后的产品。初版统一采用：

# **钱途有界**

“钱途”同时指青年人的资金安排与未来生活目标；“有界”直接对应本项目最重要的技术命题：**Agent 只能在银行事实、用户策略、资金安全与授权范围共同形成的边界内自主行动。**

一句话定义：

> 以工行可信账户事实为底座，帮助青年用户确认动态资金策略；系统持续保护固定资金义务、基本生活准备金和长期目标，在安全且已授权的空间内自主完成固定资金动作、目标储备和低风险闲置资金配置，只有当新事实真正改变自主行动边界时才请求人工介入。

主赛道：**青年群体服务**。  
技术副标签：金融安全、数字金融、可审计 Agent。

## 1. 给 Codex 的总执行指令

将本文件原样放入仓库根目录，并创建 `AGENTS.md`，把本节内容写入其中。

### 1.1 总原则

1. 严格按任务编号顺序实现，不自行扩大产品范围。
2. 所有金融动作均为**模拟动作**，不接真实工行账户、真实支付接口或真实理财产品交易接口。
3. LLM 仅允许用于：
   - 将自然语言转成候选结构化策略；
   - 解释决策；
   - 发现可能的周期性模式。
4. LLM 不得直接决定金额、权限、资金安全、策略状态、产品适配和最终执行。
5. 核心决策必须由确定性代码完成，并可通过固定输入稳定复现。
6. 未到账收入永远不能扩大今天的自主资金边界；未来收入只可展示，不可计入安全资金。
7. 用户自己的普通消费只是账户事实。系统不做生活服务、不推荐商户、不评价用户该不该消费。
8. 不接跨行聚合；现在和未来都以工行体系内账户、账单、目标账户和低风险产品为闭环。
9. 每完成一个任务，必须同时完成：实现、单元测试、必要文档、迁移脚本或示例数据。
10. 不允许用假数据冒充实测结果。企划书中的效果数字必须来自可复现测试；尚未测得的数字留空或标记为“待实验”。

### 1.2 每个任务的固定交付格式

Codex 每完成一个任务，在 `docs/progress/<task_id>.md` 写入：

- 完成内容；
- 新增或修改的文件；
- 关键设计选择；
- 已运行的命令；
- 测试结果；
- 尚存限制；
- 下一任务的前置条件。

## 2. 初版目标与最终验收

### 2.1 初版要证明什么

初版不试图证明“AI 比人更会理财”，只证明四件事：

1. **余额不等于可自主资金。** 系统能将固定义务、生活准备金、目标储备和应急缓冲从账户余额中分离出来。
2. **用户授权的是策略，不是一次性数字。** 经用户确认后，策略可持续生效、修改、暂停、到期和撤销。
3. **Agent 只在交集内行动。** 自主动作必须同时满足资金安全、用户授权、资产流动性和证据充分性。
4. **只有跨越行动边界才打扰用户。** 状态变化未改变动作集合时静默更新；需要赎回、目标冲突或新授权时才提示。

### 2.2 初版演示必须跑通的三条黄金链路

#### 链路 A：工资到账后的自动资金安排

- 工资到账，成为 `BANK_CONFIRMED` 事实；
- 系统保护房租、信用卡还款、用户确认的生活准备金和应急缓冲；
- 按买车目标的 `[min, target, max]` 储蓄范围自动划转；
- 计算剩余稳健自主资金；
- 在用户允许的活期、T+0/T+1现金管理、定存候选中做有限优化；
- 展示为什么本次没有询问用户。

#### 链路 B：自然语言创建未来目标

用户输入：

> “明年十月前想攒三万买车，每个月尽量存两千，资金别锁太久。”

系统：

- 生成结构化候选策略；
- 展示目标金额、期限、月度最低/建议/最高储备、优先级、可延期程度和资产策略；
- 用户修改并首次确认；
- 策略进入 `ACTIVE`；
- 后续新增资金在授权范围内自动分配。

#### 链路 C：大额消费后的安全恢复

- 用户自己发生一笔较大消费；
- 系统将其视为新的银行事实，不评价消费本身；
- 重新计算后发现部分已配置资金退出自主安全区；
- 若赎回无显著损失且原策略已授权，自动赎回并通知；
- 若涉及定存提前支取损失或新的未授权后果，转为请求用户确认；
- 展示完整决策轨迹和策略版本。

### 2.3 初版验收红线

以下任一项未满足，不算初版完成：

- 未来未到账收入被计入当前自主资金；
- LLM 输出可绕过确定性策略引擎；
- 固定支出、生活准备金或目标资金被错误当成闲钱；
- 定存提前支取存在损失却被自动执行；
- 策略修改后仍沿用旧版本权限；
- 任何自动动作无法回答“为什么可以做”；
- 演示依赖手工改数据库或写死结果；
- 测试结果无法从运行 ID 追溯。

## 3. 初版范围与明确不做的内容

### 3.1 初版支持

- 单一青年用户；
- 工行体系内模拟的：活期账户、信用卡账单、目标储备账户、现金管理账户、定存账户；
- 银行已确认的余额、流水、账单和已有资产；
- 用户主动补充的未来目标或外部义务；
- 周期性固定资金义务：房租、水电、信用卡还款；
- 动态生活准备金策略；
- 应急缓冲；
- 一个或两个长期储蓄目标；
- 新增资金按目标策略自动储备；
- 本人账户、目标账户和低风险资产之间的内部划转；
- 已确认固定收款关系的周期性对外转账；
- 用户临时发起的对外转账，仅做解析、消歧和执行，不由 Agent 自己产生转账意图；
- 活期、T+0/T+1现金管理、定期存款三类模拟资产；
- 安全恢复、策略版本和决策证据回溯。

### 3.2 初版不做

- 跨行账户聚合；
- 美团、外卖、购物、商户推荐等生活服务；
- 股票、基金、黄金、衍生品或任何本金波动型资产的自主投资；
- 收益预测、市场择时和“推荐哪只产品”；
- 贷款审批、授信和征信判断；
- 用户全部消费的反欺诈或异常交易模型；
- 任意自然语言策略编程；
- 真实资金、真实工行接口和真实个人数据；
- 将模型预测的未来工资、奖金或回款计入当前安全边界；
- 把“过去经常发生”直接当成未来必然义务。

## 4. 产品行为规则

### 4.1 三档自主等级

系统每次产生金融动作时，只允许输出四种结果：

```text
AUTO_EXECUTE   已有策略授权、资金安全、证据充分，可自主执行
ASK_ONCE       一个关键事实或新后果需要用户确认
ADVISE_ONLY    超出自主权限，只给方案和影响分析
BLOCKED        违反硬约束、数据不足或动作不在支持范围
```

### 4.2 Agent 可自主产生的动作

- 执行已经确认的周期性固定资金义务；
- 在 `[min, target, max]` 范围内为目标储备新增资金；
- 本人工行账户之间划转；
- 将稳健自主资金配置到允许的低风险资产；
- 在已授权、无显著损失的条件下自动赎回以恢复安全边界；
- 对已经确认的固定收款账户执行周期性转账。

### 4.3 Agent 不能自主产生的动作

- 向新收款人发起转账；
- 为用户创造一个新的消费目的；
- 擅自提高目标储蓄上限；
- 擅自改变用户目标资金的归属；
- 在目标之间挪用已归属资金，除非用户提前授权了明确规则；
- 自动买入本金波动型资产；
- 因为预计未来收入即将到账而提前放松安全边界。

## 7. 核心数据模型

金额统一使用整数分 `*_cents`，日期时间统一使用带时区的 UTC 存储，前端按用户时区展示。

MODEL_INFERRED          模型或统计方法形成的候选推断

## 8. 核心算法

### 8.1 生活准备金估算

初版采用可解释的滚动窗口分位数，不训练预测模型。

算法：

1. 取最近 `lookback_days` 的交易；
2. 仅保留用户确认过的基本生活类别；
3. 排除明确标注为一次性的支出；
4. 计算所有连续 `horizon_days` 窗口总额；
5. 取指定分位数作为基础准备金；
6. 加上用户确认的额外缓冲；
7. 输出：建议值、历史区间、被排除的一次性支出、计算版本；
8. 用户第一次确认后，才成为硬约束策略。

测试要求：

- 相同数据必须得到相同结果；
- 单次大额消费被标注为一次性后，不应显著抬高生活准备金；
- 数据不足时必须输出 `INSUFFICIENT_HISTORY`，不得伪造精确建议。

### 8.2 自主资金边界

初版按日投影未来 90 天，硬规则如下：

- 当前余额为事实；
- 未来收入全部按 0 处理；
- 固定义务、最低生活准备金、应急缓冲、目标最低储备均为受保护资金；
- 已归属目标的资金默认不能跨目标挪用；
- 已配置资产只有在赎回或到期后才视为可用现金；
- 任何时点的可支付现金不得低于该时点剩余受保护需求。

提供函数：

```python
compute_boundary(snapshot, active_policy_versions, positions, products) -> BoundaryResult
```

返回：

- `safe_idle_cents`
- `protected_cents_by_reason`
- `max_allocatable_by_product`
- `blocking_constraints`
- `boundary_hash`
- `calculation_trace`

### 8.3 产品可行性与有限优化

初版不预测收益，只使用产品目录中的固定模拟属性：

- 年化展示收益；
- 锁定期；
- 赎回时延；
- 最低起投；
- 提前支取损失；
- 是否允许自动操作。

执行顺序：

1. 过滤不在用户资产授权中的产品；
2. 过滤本金风险等级不合格的产品；
3. 过滤在预计资金需要时间前无法变现的产品；
4. 计算每个产品的最大安全配置金额；
5. 在合格产品中按“净模拟收益优先、流动性更短作为并列优先”选择；
6. 初版最多选择一个产品，避免伪装成复杂资产配置系统。

### 8.4 自主等级判定

`AUTO_EXECUTE` 必须同时满足：

- 来源为用户已确认的活动策略或用户即时明确指令；
- 当前边界允许；
- 额度在授权上限内；
- 产品/收款对象在允许范围内；
- 关键字段唯一；
- 不产生新的显著费用、损失或本金风险；
- 使用的是最新策略版本；
- 动作执行可幂等重放。

只要一个关键事实不确定且不同取值会改变动作，就输出 `ASK_ONCE`。即使信息完整也超授权，则输出 `ADVISE_ONLY`。

### 8.5 安全恢复

边界收缩时：

1. 计算需要恢复的现金缺口；
2. 依次尝试 T+0、T+1 和到期资产；
3. 只允许原策略授权、无显著损失的自动赎回；
4. 定存提前支取存在损失时必须转 `ASK_ONCE`；
5. 恢复完成后生成 `ActionReceipt` 并通知；
6. 无法及时恢复时标记 `LIQUIDITY_RISK`，不得假装安全状态已经恢复。

### 8.6 决策审计

每次决策必须记录：

- 账户快照及哈希；
- 使用的策略版本；
- 证据项及等级；
- 算法版本；
- 每条约束的计算值；
- 被过滤的候选产品及原因；
- 为什么自动执行或为什么需要询问；
- 动作请求、执行回执和后续对账；
- 前一审计事件哈希与当前事件哈希。

提供 `scripts/verify_audit_chain.py` 验证链完整性。

## 12. 初版实验设计

### 12.1 对照组

- **B0：手工预算页面**——用户自己设固定金额，无 Agent；
- **B1：余额阈值法**——账户余额超过阈值就配置；
- **B2：静态规则 Agent**——只看固定支出，不看动态生活准备金、目标和流动性；
- **B3：全量确认 Agent**——每次动作都问用户；
- **P：钱途有界**——策略确认后持续运行，只在边界变化时介入。

### 12.2 指标

安全指标：

- 受保护资金违反次数；
- 未授权动作次数；
- 流动性不足次数；
- 有损赎回被错误自动执行次数；
- 使用旧策略版本次数。

自主与效率指标：

- 可安全自主动作中的自动完成率；
- 每个场景的人工介入次数；
- 不必要询问次数；
- 被过度保守闲置的资金；
- 决策和恢复时延。

可解释与审计指标：

- 动作可追溯率；
- 决策所需证据完整率；
- 审计链验证成功率；
- 失败原因是否可定位。

### 12.3 初版案例集

至少 24 个手工冻结案例：

- 6 个正常资金充足；
- 6 个目标/义务冲突；
- 4 个大额消费导致边界收缩；
- 4 个定存/流动性冲突；
- 2 个策略到期或换租；
- 2 个用户即时转账歧义。

开发案例和冻结案例必须分开；冻结后修改规则需升级版本并重新运行全部实验。

展示：

- AUTO_EXECUTE；
- ASK_ONCE；
- ADVISE_ONLY；
- BLOCKED。

强调自主性来自策略和证据，不来自大模型自信。

#### 第6页：策略与资金分层

- 动态生活准备金；
- 目标储备；

- 稳健自主资金。

#### 第8页：可审计决策

展示一条真实运行的 DecisionTrace：

- 哪些事实；

## 16. 风险与停项条件

- 如果系统只是“余额减预算”，没有时序流动性和资产恢复，项目退化为预算工具；
- 如果所有动作都要确认，项目没有分级自主价值；
- 如果所有动作都自动，项目越过授权边界；
- 如果不能实现决策回溯，不能把“可信 Agent”作为核心主张；
- 如果定存等产品只按收益排序而忽略锁定与提前支取，不得展示资产优化；
