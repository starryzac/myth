## 建议的四级验收矩阵

以下全部为**待实现、待测试**的验收建议。每项均需同时断言等级、原因、是否可执行及资金效果，不能只比对标签。`ASK_ONCE` 确认通过后可以使该笔动作可执行，但应保留它原本需要人工确认的来源，避免统计为无人工自主执行。

| 场景与输入前提 | 建议等级 | 必须验证的执行边界 |
| --- | --- | --- |
| 最新活动策略、完整证据、确定金额/对象、授权内、无新增费用损失、财务后态安全 | `AUTO_EXECUTE` | 仍经 301 锁内重新校验和幂等执行；分类结果自身不能当作银行授权。 |
| 周期支付 `auto_execute=False`，其他事实完整 | `ASK_ONCE` | 精确本笔确认前无资金效果；确认不改持续策略。 |
| range 周期支付已有可信、范围内的 `final_total` | `ASK_ONCE` | 绑定本期精确金额与业务身份；付款现金减与同笔结清保护同步。只有 max、没有本期实付依据时是 `BLOCKED`。 |
| 用户具体发起内部划转，源、目标和金额已确定 | `ASK_ONCE` | 沿用 301 明确一次确认；收入血缘只迁移，不造新增收入，不挪用目标归属。 |
| 已知完整事实显示金额、资产类别或 scope 超出持续授权 | `ADVISE_ONLY` | 可显示影响或策略修改建议；不得仅点一次确认绕过当前授权。若还违反硬约束，应优先 `BLOCKED`。 |
| 旧动作仍绑定已被替换的策略版本 | `BLOCKED` | 要求按当前版本重新准备；旧 effect/hash/确认不可移植。 |
| 已知策略暂停或撤销，但能完整计算一个新的建议方案 | `ADVISE_ONLY` | 与“执行旧动作”区分；后者仍 `BLOCKED`。建议不能创建新银行效果。 |
| 普通投资存在流动性缺口、期限不适配，或需要尚未受理的主动退出才能安全 | `BLOCKED` | 不用未来收入、展示收益或未受理本金回款填缺口。 |
| 原始及当前权限均允许无损恢复，273 点不劣且至少改善一个负点 | `AUTO_EXECUTE` | 不应因基线已有缺口而一律禁止恢复；T1 到账前实际风险仍保留，不能只因预测改善就记为已经恢复。 |
| 有效精确报价包含正费用/损失，原始及当前权限允许，且满足 301 有损恢复财务门 | `ASK_ONCE` | 绑定本金、费用、损失、净到账、原产品、版本、有效期与到账上界；确认不能突破 `after >= min(before, 0)` 且改善原负点的门。 |
| 有损方案原始或当前权限明确不允许 | `ADVISE_ONLY` | 不可把成本确认当作新增持续权限；若缺报价或事实冲突则 `BLOCKED`。 |
| 同一有限变量所有可信候选均得出相同经济动作，且每个候选均安全、已授权 | 不新增询问 | 保持该动作本身的等级；已有成本或付款确认仍是 `ASK_ONCE`，不能被“结果稳定”消除。 |
| 有限候选改变动作种类、金额、资金归属、收款人或风险后果 | `ASK_ONCE` | 询问能决定分歧的用户事实；回答后重新计算并绑定新的候选，不能沿用旧确认。 |
| 银行余额、报价、原始购买证据或身份来源缺失/冲突 | `BLOCKED` | 告知需重新获取或核对来源；用户回答不能把不可信事实变成银行确认。 |
| Agent 自行创造新收款人或新消费目的 | `BLOCKED` | 不生成可确认支付命令。 |
| 用户明确发起新收款关系，银行身份已核验，仅缺关系授权 | `ASK_ONCE` 候选语义 | 需先冻结受支持动作边界；当前没有对应执行能力时仍应明确 `BLOCKED / UNSUPPORTED_ACTION`，不能承诺确认即可付款。银行身份缺失同样阻断。 |
| 银行已经受理的原操作在之后遇到策略撤销，或读取已完成回执 | 沿用原受理事实，不重新授予自主等级 | 继续原操作结算/对账与只读历史回执核验，不能把撤销当作“未发生”并释放占用，也不能再次记账。 |

## 最小实现建议

建议增加纯分类器与薄服务适配，保持“是否允许银行执行”和“为什么需要何种介入”两层信息。以下是设计草案，不是已冻结公共合同。

- `AutonomyFacts`：动作来源、精确策略版本及生效状态、已验证权限范围、收款身份/关系状态、财务重验结果、成本后果、是否为旧载荷、证据问题，以及已有精确确认事实。不得由客户端传入一个 `authorized=True` 替代来源实体。
- `AutonomyDecision`：四级 `level`、结构化 `reasons`、所需介入类型、当前 `execution_eligible`、关联经济载荷/版本；确认事实与原始分类分开。需要修改持续策略、回答歧义、确认精确成本和刷新银行事实应是不同原因。
- 领域分类器只接验证后的事实及有限候选，不访问数据库或当前时钟；服务传入可信时钟、来源与权限。301 的 `revalidate_execution`、203/204 规划器和 205 恢复规则继续负责确定性财务判断。
- 对可执行候选沿用 301 不可变 `ExecutionEffect`、稳定 `effect_hash`、时效与锁内重验。分类器不得直接执行，不接受任意分录，也不因 `financial_only` 成功而授予自动权限。
- 先检查不支持、来源缺失、旧载荷和硬约束等阻断；信息完整下的权限不足才进入建议；只有权限及财务条件允许且需要用户决定的后果才进入一次确认；余下满足全部条件的候选才可自主。保留全部具体原因，不能用一个枚举覆盖证据差异。

可并行文件分工建议：领域 owner 负责四级 DTO、分类及表驱动测试；服务 owner 负责可信事实适配、与 301 prepare/execute 的集成及真实 PostgreSQL 测试；独立审查 owner 负责矩阵反例与性质测试；root 负责 ADR、API/合同和顺序验收。具体文件及修改权应在 301 验收后另行分配。

## 有限候选不确定性的最小边界

初版只处理一个有明确来源和有限候选的决策相关变量，候选数量设置明确资源上限；不依赖 LLM 置信度、概率预测或无限枚举。候选不能漏掉一个已知可能但不利的取值，也不能把不完整银行来源变成“用户任选一种世界”。无法建立完整有限集合时关闭执行并说明原因。

每个候选独立运行现有确定性检查。比较的经济动作签名至少包括动作类型、金额、源/目标账户、收款身份、归属目标、产品版本、费用/损失与实际到账约束。不能只比较 `READY`，也不能比较含随机 operation ID 或读取时钟的完整执行 hash；前者会漏掉资金后果，后者会制造无意义差异。稳定性签名仅用于候选比较，不能替代真正的确认 hash。

若所有候选经济动作相同，但任一候选不安全、未授权或来源不足，不能宣布稳定可执行。若差异只在展示收益且不影响所选动作、成本、归属或安全结果，不新增询问。若差异会改变这些结果，则展示具体分歧，用户回答后重新准备；旧候选和旧确认不得自动搬用。

本项不实现 FULL-504 Minimax 问题选择、FULL-505 多轮问题状态机、FULL-507 通知去重节流或 FULL-302 多目标联合优化。保留可扩展数据结构即可，不以预留接口声称这些能力已经完成。

## 进入实现前需冻结的口径

1. **新收款关系与不支持动作：** 分类层可表达用户主动发起后的确认需要；是否提供实际的新收款支付必须有独立身份、明确用户意图和受支持执行协议。不能仅加一个等级标签便扩大 301 的动作范围。
2. **权限否定与证据缺失：** 已知、完整但超授权的可计算方案为建议；银行证据缺失或冲突仍阻断。旧命令不可通过新策略或新确认复用。
3. **候选稳定性与确认记录：** 使用经济后果签名；明确候选上限和来源完整要求；已确认的 `ASK_ONCE` 保留人工介入来源，不重记为纯自动执行。
