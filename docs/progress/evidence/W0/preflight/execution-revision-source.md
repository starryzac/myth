## 2. 先修正规格中的易返工点

### 2.1 边界重算与人工询问不是同一个事件

将原完整计划 11.4 中“自主金额下降、已有资产需要赎回”等条件定义为重算/恢复的候选触发，而非一律弹窗。

建议合同：

```text
新事实 -> 重新计算资金与授权边界
       -> 已授权且确定安全：自主执行，记录并展示
       -> 不确定信息确实改变可执行动作：提出一个必要问题
       -> 新损失/新收款/新权限：请求明确确认
       -> 无安全方案：阻止执行并说明
```

预授权、无损、可及时到账的赎回不应重复询问。T1 尚未到账时保留真实缺口；有损提前支取不能因“恢复安全”绕过确认。

### 2.2 硬约束先于优化目标

现金守恒、用户授权、义务保护、禁止跨目标挪用、产品额度与 max 上限等，应定义为可行域约束，不是能够被较高优化收益抵消的软惩罚。

在可行域内再按词典序优化目标短缺、优先级、延期、target 偏离与调动次数。明确哪些“最低储备”是硬保护、哪些是新收入不足时允许报告的贡献短缺；不改变既有用户授权来制造可行解。不得使用未证明等价的浮点大权重近似偷换词典序。

### 2.3 365 日投影不等于依靠全年未来工资

明确区分展示期限、已确认义务保护期限和资产可用时间。若所有 365 日已确认义务都属于硬保护，且未来收入一律不计，那么当前可自主资金为零可能是正确结果。

例：现有现金 10000 元，已确认未来一年每月房租 2000 元，仅房租保护就超过现金。不得通过偷偷加入未来工资或忽略已确认房租提升自主率。应在规格和界面解释原因，并把义务有效期作为明确可确认的策略字段。

### 2.4 “最小”须给出精确定义

冲突集区分“删除任意一个约束就不再冲突”的子集极小与“所有冲突集中约束数量最少”的最小基数。删除式算法只能按实际证明的性质命名；任务要求若涉及更强最小性，应增加有限域精确求解及独立枚举核验，不能改名降低要求。

最小问题选择须定义候选世界、问题可回答集合、回答后残余分歧的度量及并列规则。一步 minimax 不自动等于整棵问答树总问题数最少。产品、报告与测试使用同一实际算法定义。

动作等价至少比较动作类型、金额、收款关系、源/目标账户、目标归属、风险/费用/损失、到账期限及适用权限。两个世界都返回 AUTO_EXECUTE 不代表相同动作。候选空间不完整或超出容量时保留 UNKNOWN/需确认，不能假称所有世界一致。

### 3.3 第二层：只有第一层不足时再改变读取结构

再考虑把普通展示、当前执行安全重验、显式全历史审计分为不同调用路径。展示若使用已验证读模型，必须显示验证范围、时间、数据版本与过期状态，不得把旧 VALID 渲染成刚刚验证。

任何增量审计必须有可信前缀与被保护的不可变存储条件，能检测约定威胁模型中的历史改写/删除/截断；原全量核验仍保留。跨请求缓存、增量 checkpoint 或新审计版本是独立变更，需要 ADR 和定向故障测试，不能夹带在 UI 优化里。

### 3.4 通过条件

### W2：共同合同与可靠执行底座

### W3：现金边界与多目标约束

形成无数据库副作用的统一评估接口，承接已有 boundary/domain，而非平行重写第二个引擎：

```text
evaluate(snapshot, policy_versions, product_versions, candidate_actions)
    -> feasible_actions, constraints, rejected_reasons, trace
```

当前执行与规划视图的数据流明确分离。365 日有效期、闰年/月末、到账期限、重复事件、归属守恒均进入测试。目标优化、冲突定位、最小修复与边界差异解释复用同一约束表示。

正常路径使用确定性有限优化；另写小规模独立枚举真值，避免用同一个求解器的结果证明自身正确。超过声明容量或求解不完整时明确状态，不能返回未经验证的“最优安全解”。

### W4：多资产、定存与恢复

在已有单产品过滤、不可变产品版本、申购赎回执行和资产归属上增量实现组合优化、定存梯度、到期再评估与组合恢复。

产品差异表达为本金、起投/额度、可用日期、提前支取损失、授权、目标期限等共同属性。定存梯度是受约束的一组批次，不新建一套完全不同的资金执行器。全部原定产品类别仍须有实际行为测试。

每个组合先通过安全与授权过滤，再比较收益、流动性和换手；不得以收益抵消保护约束。周期付款、新收款意图边界、每批限额、到期策略撤销、有损恢复确认分别测试。

### W5：候选编译与最小必要介入

编译/规律发现/节日准备金只产生候选；保持外部 LLM 默认关闭及可离线运行。节日历注明来源和有效年份，不能凭陈旧日历推导新的资金义务。

## 6. 并行规则：按稳定接口分工，不按 Agent 数量分工

建议最多三个主要工作面：金融内核与数据库；前端与体验；独立测试真值、实验与材料。不是要求必须有三名成员，也不是三个 Agent 可以同时随意编辑全部文件。

共享 models、迁移、执行状态机、审计协议各设单一集成负责人。独立 worktree 与明确文件边界；跨工作面先冻结 DTO、错误语义和版本约定，再并行。审查者保留独立负例/小规模真值，不全部由实现者的同一算法自动生成。

一条资金链严格顺序；数据库完全隔离且资源允许时有限并发。禁止通过同时执行多个重型同库流程制造“并行加速”。

## 7. 验证：保留用户已经确定的两节点规则

完整测试仅在初版与完整版两个验收节点运行，失败可在该节点修复重跑。开发期依现有 `verification-map.md` 做模块及直接依赖的定向验证；不是取消集成测试。

先快检查，再依赖它们的慢检查。金融守恒、重复扣款、UNKNOWN、迁移必须覆盖真实 PG 集成。共享上下文变更必须覆盖实际消费者；不能只选择最容易通过的两个测试。前端类型、组件和受影响页面测试相应执行。

## 9. 优化空间的估算方式

目前没有逐任务工时、Agent 成本与 profile 分解，不能给实测的总体节约百分比。建议先以相同工作量的两个代表性任务收集：新实现、返工、等待验证、证据整理四类成本。

仅作预算情景：原剩余成本 100 单位，由新实现 45、验证 25、返工 20、文档证据 10 构成；不减少新实现，分别减少后三项的 50%、40%、50%，则成本为 45+12.5+12+5=74.5，节约 25.5%，吞吐约为原来的 1.34 倍。这不是仓库实际工时比例，也不是效果承诺。

建议把总剩余投入降低 20%—35%作为待验证的管理目标；不能承诺整体两倍速度。长审计读取可能取得更高的局部加速，但必须保持相同数据与安全语义才可报告。真人研究与独立审查不能由程序运行速度替代。
